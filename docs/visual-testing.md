# 画面の回帰テスト

Playwright の Chromium で Expo の本番 Web 書き出しを表示し、390×844、320×740、390×640、1280×1000 の4サイズ・128テストを検証します。認証画面、規約の表示、メール確認、初回登録の全6ステップ、空のデッキ、証言のあるデッキ、カード詳細、装飾、プロフィール、設定、交換、つながり、自己PR、パスワード再設定、アカウント削除を対象にします。

ヘッダー、チャレンジバナー、自己PRバナー、先頭と末尾のカードについて、元HTMLとの位置・寸法の差が1px以内であることも検証します。基準画像を更新しても、この照合は省略されません。

メールでの登録、同意、確認コードの入力、プロフィール保存、再読み込み、ログアウト、再設定メールのリンクからのパスワード変更、新しいパスワードでの再ログイン、削除確認メールからの確定・全セッションの失効・端末保存データの消去も実際の UI と API で実行します。確認コード、再設定リンク、削除確認リンクはテスト専用の受信箱から取得します。変動する再送カウントダウンだけを確認画面の画像比較から除外します。

```sh
npm ci
npx playwright install chromium
npm run test:vrt
npm run test:vrt:report
```

Node 22.13以上と OpenSSL が必要です。9010・9012番ポートを使用します。テスト専用の証明書を生成し、ローカル HTTPS から実際の Workers を呼び出します。D1・R2 はテスト実行ごとに起動する独立したローカル環境です。メールとプッシュの外部送信は捕捉します。実際のAPIで登録・認証・交換・証言を作成するため、本番アプリの通信をモック成功応答に置き換えません。

基準画像は404枚で、OSごとに保存します。装飾の4タブとシール4枚の状態も参照HTMLと比較します。現在の基準画像は macOS 用です。別 OS の実行結果はフォント描画が異なるため、その環境で画像を確認してから追加してください。

```sh
# 変更内容を確認したうえで、明示的に基準画像を更新する
npm run test:vrt:update
git diff -- e2e/visual/baselines
```

認証画面、デッキ、カード詳細、装飾、交換、印象を贈る画面、自己PRでは `design/flocka-v2-blue-prototype.html` を別ページで表示し、元デザインとの比較画像とピクセル差分の計測結果もレポートに添付します。参照ページの JSX・CSS・アセットは変更せず、外部スクリプトとフォントの読み込みだけローカルに置き換えます。参照画像との比較は差の調査用であり、回帰テストの成功だけでデザインの完全一致を意味するものではありません。OAuth の未設定状態など、実際の設定による表示差も確認対象です。

参照 HTML のサンプルには同じ相手からの複数の印象があります。本実装の「印象は交換相手ごとに1回」の制約を維持するため、テストの実データでは一つを場面のメモとして送っています。テスト専用の相手プロフィールも元デザインの名前・役割・アイコン・関心を実際の API で保存します。ブラウザごとにローカルのクライアントIPを分け、認証の回数制限を無効化せずに独立したテストを実行します。

実機の Safe Area、カメラ、BLE、OS の通知、OAuth の認証先、メール配信は、この Web VRT では検証されません。

装飾のテストでは、シール4枚の上限、取り外し、配置位置の再利用、色と模様の保存、再読み込み、初期化を実際のAPIで確認します。通信をオフラインにした場合は成功表示せず、再接続後に保存できます。実際の保存リクエストを保留している間に別画面へ進み、完了後も現在の画面が維持されることも確認します。編集用のユーザーはテストごとの独立した名前空間で作成し、他の画面テストのデータを変更しません。

直接URLで開いたカード画面は、初回読込中もURLを維持します。同期通信だけを失敗させ、エラーからの再試行後も指定したカードが開くことを検証します。成功応答を模擬する検証ではありません。

印象を贈る画面は、言葉の選択・理由・自由入力・要約・送信完了を原本と比較します。選択肢にはラジオボタンの意味を持たせ、元イラストと配置を検査します。画像の比較に加え、入力欄と主要な領域は原本との寸法差を1px以内に検査し、送信後の再読み込みでは実APIに保存された本文を確認します。

場面メモは相手選択・強み選択・本文入力・完了を7状態で原本と比較し、相手がいない場合を別に検査します。各段階での操作禁止・選択状態・戻った場合の入力保持、実API上の本文・強み・交換IDも検査します。相手一覧の説明には保存された出会いの場所を使うため、原本の固定説明とは文字列が異なります。

つながった人は一覧・送信済み・解除確認・解除後・空一覧を原本と4サイズで比較し、承認待ちは実APIで作成して別に検査します。解除の通信失敗と不正な成功応答では解除済みとして扱いません。受付後に同期が失敗した場合は、解除を再送せず同期だけを再試行します。届いた証言が残ることもAPIで確認します。
